# Design package v1 (`export_design_package`, `validate_design_package`)

A design package is one folder (default `<project>/design-package/`) that holds the current design as
versioned JSON files plus a LandXML 1.2 file, described by `manifest.json`. It is a data exchange
format. No Civil 3D or OpenRoads plug-in reads it yet; the Civil 3D API mapping below is a
specification only, with no Windows code in this repository.

Schemas (JSON Schema 2020-12) are committed in [`schema/design-package/v1/`](../schema/design-package/v1)
and generated by [`scripts/gen_package_schemas.py`](../scripts/gen_package_schemas.py). `schema_version`
is `1.0.0`; a change that breaks a reader will raise the major version and use a new `v2/` folder.

## Layout

```
design-package/
  manifest.json        schema version, created, status, generator, project, units, CRS, source run, files[] with role, schema, bytes, sha256
  alignments.json      alignments: elements (line / arc / spiral) with stations, ends, directions, radii, turn, arc centre
  profiles.json        design profile (PVIs, curve lengths, grades, 10 m samples) and EG profile (10 m samples from the EG TIN)
  superelevation.json  per curve: e, runout start, level crown, full super start/end, level crown out, runout end, method
  assemblies.json      ordered subassembly-like parameter sets per side, plus the raw civil-mcp assembly parameters
  corridors.json       corridor: alignment, profile, regions (station range, assembly, frequency, targets), results
  surfaces.json        EG and Corridor FG: references into design.xml (surface name, counts, elevation range, breaklines, boundary)
  pipes.json           networks: structures (E, N, rim, sump) and pipes (from, to, length, diameter, material, inverts, slope, design flow)
  parcels.json         parcels (outer rings and holes, area, zoning, no-go) and the ROW polygon (daylight + buffer)
  quantities.json      corridor cut/fill, pavement layer volumes, mass haul (if computed), bill of quantities rows
  sheets.json          sheet list from sheet-register.csv and construction-register.csv of the run
  design.xml           LandXML 1.2 of the same design (see landxml.md)
```

### Units and CRS

- All package JSON is canonical SI (`"units": "SI"` in every file): m, m², m³, m³/s, m/m, degrees.
  Directions are grid azimuths in degrees clockwise from north. Radius `null` means infinite.
- `manifest.units.display_system` records the session units (`SI` or `US`, with `display_foot`), and
  `manifest.units.landxml_linear_unit` the unit of `design.xml` (`meter`, `foot` or `USSurveyFoot`).
  `design.xml` follows the session units unless `landxml_units` is given.
- `manifest.crs.epsg` is the horizontal EPSG code when known (the demo: 32610, WGS 84 / UTM 10N).
  No vertical datum is recorded.

### Source run

`manifest.source_run` gives the project folder, the audit log file, its sequence number and SHA-256
head at export time, so a package can be traced to the hash-chained run log. Status is always
`PRELIMINARY`.

## Validation

- `export_design_package` validates the folder after writing and returns the result.
- `validate_design_package` (any folder, relative to the project or absolute) checks the manifest and
  each JSON file against the embedded schemas, recomputes sizes and SHA-256, and checks the LandXML
  linear unit. The Rust validator implements the keywords the v1 schemas use: `type`, `const`, `enum`,
  `required`, `properties`, `additionalProperties`, `items`, `minItems`, `maxItems`, `minimum`, `$ref`.
- CI runs [`scripts/package_check.py`](../scripts/package_check.py) on the SI and US demo packages: full
  validation with the Python `jsonschema` package (Draft 2020-12), hashes, XSD validation of the
  package LandXML, and content cross-checks against the run's own files. Run of 2026-10-21 (UTC+8),
  20 / 20 checks pass in each run, including:

| Check | SI | US |
|---|---|---|
| manifest + 10 JSON files, schema errors | 0 | 0 |
| 11 files, size or SHA-256 differs from manifest | 0 | 0 |
| package LandXML XSD errors | 0 | 0 |
| alignment chain: end to next start, max gap | 4.66e-10 m | 4.66e-10 m |
| alignment tangency at joins, max direction change | 0° | 0° |
| element ends vs LandXML `End` (13 elements), max | 5.45e-7 m | 1.91e-7 m |
| design PVIs vs LandXML, max | 4.96e-7 m | 1.44e-7 m |
| pipes (25): inverts, diameters, lengths vs `network-*.json` | 0 m | 0 m |
| sheets vs registers (52 rows) | 0 difference | 0 difference |

- `cargo test` (`crates/civil-core/tests/package.rs`) checks that the subset validator rejects bad
  enums, negative lengths, short arrays, wrong units, unknown and missing keys, and that
  `validate_dir` reports missing roles and tampered files.

## Content notes

- **Alignments**: one alignment (civil-mcp designs one at a time). `station_equations` is always empty
  (civil-mcp has none). Spirals are clothoids.
- **Assemblies**: civil-mcp's assembly is translated into an ordered list per side: `lane` (width; cross
  slope from superelevation), `shoulder` (width, slope, paved), `curb_gutter`, `sidewalk`, `ditch` (cut
  only), `wall` (the wall rule), `daylight` (cut and fill slopes, benches, target EG), and one
  `pavement_structure` (layers and thicknesses). These are parameter sets that resemble subassemblies;
  they are not Civil 3D stock subassembly definitions. `source_parameters` keeps the exact civil-mcp input.
- **Corridors**: one region covering the corridor. `frequency` gives the largest sample spacing on
  tangents, curves and spirals plus the overall minimum and maximum spacing (civil-mcp samples at a fixed
  interval and adds critical stations). Targets: EG for daylight, curve widening as a width target, the
  wall rule as an offset target. Intersections and grading objects are not in the package.
- **Surfaces**: geometry stays in `design.xml`; `surfaces.json` lists what to read from it.
- **Parcels**: rings split by orientation (counter-clockwise outer, clockwise holes). The ROW polygon is
  the corridor daylight line offset by the ROW buffer, a screening line only; a legal ROW plan needs a boundary survey.
- **Quantities**: values as computed by civil-mcp (average end area, bank volumes); the BoQ rows are the
  same as `boq.csv` in SI.
- **Sheets**: rows read from the registers the drawing tools wrote. Titles are as written, so a US run
  shows US stationing in titles.

## Intended Civil 3D API mapping (specification only)

This is how a future Civil 3D .NET add-in could build native objects from a package. No such add-in
exists in this repository, nothing below has been compiled or run, and the class and method names must be
checked against the Civil 3D .NET API reference of the target release before implementation.

| Package content | Intended Civil 3D .NET API | Notes |
|---|---|---|
| `alignments[]` | `Alignment.Create(civilDoc, name, siteId, layerId, styleId, labelSetId)`, then `Alignment.Entities.AddFixedLine`, `AddFixedCurve`, `AddFixedSpiral` per element in station order; `Alignment.ReferencePointStation` from `sta_start` | fixed entities reproduce the exported geometry exactly; free/floating entities and PI-based layout are not attempted |
| design profile | `Profile.CreateByLayout(name, alignmentId, layerId, styleId, labelSetId)`, then `Profile.Entities.AddFixedTangent` between PVIs and `AddFreeSymmetricParabolaByLength` at each PVI with `curve_length > 0` | |
| EG profile | `Profile.CreateFromSurface(name, alignmentId, surfaceId, layerId, styleId, labelSetId)` after the EG surface exists | the package samples are there for checking the built profile |
| `superelevation.json` | the alignment's superelevation curves and critical stations (`Alignment.SuperelevationCurves`, critical station add calls) | API coverage of superelevation editing differs by release; LandXML `Superelevation` import is the fallback |
| `assemblies.json` | `CivilDocument.AssemblyCollection.Add(name, ...)` and stock subassemblies imported from the catalog, parameters set from `params` (lane width and slope, shoulder, curb, ditch, daylight slopes) | mapping each `kind` to a stock subassembly is a design decision for the add-in |
| `corridors.json` | `CivilDocument.CorridorCollection.Add(name)`, `Corridor.Baselines.Add(name, alignmentId, profileId)`, `Baseline.BaselineRegions.Add(name, assemblyId, sta_start, sta_end)`, frequency on the applied assembly settings, targets set from `targets` (EG surface for daylight) | |
| `surfaces.json` + `design.xml` | Civil 3D has no public .NET LandXML import call; import `design.xml` with the LandXML import command, or build `TinSurface.Create(db, name)` and add points, breaklines (`BreaklinesDefinition`) and the outer boundary (`BoundariesDefinition`) | see the forum source in landxml.md |
| `pipes.json` | `Network.Create(civilDoc, name)`, `Network.AddStructure(...)` at E, N with rim and sump, `Network.AddLinePipe(...)` between structures, then inverts and diameters from the package | requires a parts list with matching sizes |
| `parcels.json` | parcels in a site from closed boundaries (outer rings), with holes as separate interior boundaries | |
| `quantities.json`, `sheets.json` | none (reference data for comparison with Civil 3D's own quantity takeoff and sheet set) | |

## Limits

- No reader exists in Civil 3D or ORD; the package has only been read by civil-mcp's validator and the
  Python checks.
- One alignment, one design profile, one corridor region per package.
- No station equations, no intersections, grading objects or walls as objects (walls only as an
  assembly rule).
- The Rust validator covers a keyword subset; the full JSON Schema check runs in CI with `jsonschema`.
